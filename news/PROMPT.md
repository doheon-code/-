# 데일리 정치·경제 브리핑 작성 지침

매일 예약 실행(Routine)이 이 파일을 읽고 그대로 따릅니다. 내용을 바꾸고 싶으면 이 파일만 고치면 됩니다.

## 저장 구조

**모든 기록의 원본은 웹페이지(Artifact) 하나입니다**: https://claude.ai/artifact/G2cofu9uoG3YaKEeYcKMP2
예약 실행 세션에는 GitHub 푸시 권한이 없으므로 저장소가 아니라 이 페이지를 읽고, 더하고, 다시 올립니다.

| 페이지 안의 파일 | 역할 |
|---|---|
| `briefings.json` | 모든 날짜의 브리핑 원문 + 추적 이슈 + 전망 기록 (원본 데이터) |
| `tools/build_site.py` | `briefings.json` 을 작업 폴더로 풀고(unpack) 다시 묶는(pack) 도구. 형식 검사 포함 |
| `tools/PROMPT.md` | 이 지침 |
| 페이지 본문(index) | 화면. 매번 그대로 다시 올린다 |

작업 폴더(`W`)는 세션의 scratchpad 안에 만든다. 풀면 이렇게 된다.
- `W/briefings/YYYY-MM-DD.md` — 날짜별 브리핑 (과거 날짜는 고치지 않음)
- `W/summaries/week-YYYY-MM-DD.md` — 주간 요약 (날짜는 그 주 월요일, 기간은 월~일)
- `W/summaries/month-YYYY-MM.md` — 월간 요약
- `W/tracker.json` — `issues`(경과·전망·과거 사례, 확률 변화 기록), `forecasts`(확률·마감일·결과), `indicators`(날짜별 시장 지표)

## 할 일

1. 기준일: 한국 시간(KST) 오늘 날짜. 대상은 **직전 24시간**의 뉴스.
2. **불러오기**: Artifact 도구로 위 URL을 `action: "read"` 로 읽는다 (페이지 본문이 저장된 로컬 파일 경로를 기억해 둔다). 이어서 `action: "read"`, `paths: ["briefings.json", "tools/build_site.py", "tools/PROMPT.md"]` 로 세 파일을 받는다. 그다음 `python3 <받은 build_site.py> unpack <받은 briefings.json> W` 를 실행한다.
3. **오늘 할 일 확인**: `python3 <build_site.py> todo W` 를 실행한다. 여기 나온 일은 빠짐없이 한다. 하루를 건너뛰었어도 빠진 일은 다음 실행에서 다시 나온다.
   - "전망 채점"이 있으면 **가장 먼저** 한다 (아래 "전망 자동 점검 규칙").
   - "주간 요약 작성", "월간 요약 작성"이 있으면 오늘 브리핑을 쓴 뒤에 작성한다 (아래 "주간·월간 요약 규칙").
   그다음 `W/tracker.json` 과 최근 브리핑 2~3개를 읽고 추적 중인 이슈를 확인한다.
4. `WebSearch`로 아래 네 영역을 각각 2~3번 이상 검색한다 (영어·한국어 모두). 추적 중인 이슈마다 새 소식도 검색한다. (WebFetch는 대부분의 뉴스 사이트가 막혀 있으므로 검색 결과 위주로 쓴다.)
   - 🌍 세계 정치 (전쟁·외교·정상회담·선거)
   - 💹 세계 경제·시장 (미국 증시, 연준·주요 중앙은행, 유가, 달러, 미·중 무역)
   - 🇰🇷 한국 정치 (대통령실, 국회·여야, 외교·안보, 남북관계)
   - 🇰🇷 한국 경제 (코스피·환율, 수출·반도체, 물가·금리, 정부 정책, 주요 기업)
5. `W/briefings/YYYY-MM-DD.md` 를 아래 형식으로 작성한다. 오늘 날짜 파일이 이미 있으면 최신 소식으로 고쳐 쓴다.
6. `W/tracker.json` 을 갱신한다 (아래 "이슈 추적 규칙"). 오늘 날짜의 `indicators` 한 줄도 추가한다.
6-1. todo 에 주간·월간 요약이 있으면 지금 작성한다.
7. **묶기**: `python3 <build_site.py> pack W W/out/briefings.json` 을 실행한다. 형식 오류가 나면 tracker.json 을 고쳐 다시 실행한다. 출력된 브리핑·요약·전망 개수가 불러올 때보다 줄었으면 절대 올리지 말고 원인을 찾는다. "아직 남은 할 일"이 출력되면 그 일을 마치고 다시 묶는다.
8. **올리기**: Artifact 도구로 publish 한다. `url` 은 위 주소, `file_path` 는 2단계에서 받은 페이지 본문 로컬 파일, `files` 는 `{"briefings.json": "W/out/briefings.json"}` 이다 (W는 실제 경로로 바꾼다). `icon` 은 넣지 않는다. 새 URL이 생기면 안 된다. 충돌로 거부되면 다시 불러와서 합친 뒤 올린다.
9. 세션의 마지막 답변은 "오늘의 핵심 3줄" + 웹페이지 주소로 짧게 끝낸다 (이 내용이 알림으로 간다).

## 작성 원칙 (사실 부분)

- 한국어로 쓴다. 고유명사는 필요하면 영문을 함께 적는다.
- 영역별로 3~5개 항목을 쓰고, 항목마다 1~3문장으로 쓴다. **사실 → 의미(왜 중요한가)** 순서로 쓴다.
- 숫자(지수, 금리, 환율, 유가)는 검색 결과에 나온 값만 쓴다. 출처마다 다르면 범위로 쓰거나 생략한다. 추측으로 숫자를 만들지 않는다.
- 확인되지 않은 소식은 쓰지 않거나 "보도에 따르면"으로 표시한다.
- 정치적으로 한쪽에 치우친 표현을 피하고, 쟁점은 양측 입장을 함께 적는다.
- 주말·공휴일로 시장이 닫혀 있으면 마지막 거래일 기준임을 명시한다.
- 출처는 아래 "출처 기록 규칙"을 따른다.

## 출처 기록 규칙

어떤 매체에서 무엇을 가져왔는지 나중에 확인할 수 있도록, 모든 사실에 출처를 남긴다.
웹페이지의 "출처 기록" 탭과 브리핑 아래 "이 브리핑의 출처" 목록은 **본문 링크에서 자동으로 만들어진다**. 링크가 없는 사실은 기록에 남지 않는다.

1. **사실 항목마다 링크를 최소 1개 단다.** 항목 끝에 `([매체명](기사 URL))` 형태로 쓰고, 여러 개면 쉼표로 잇는다. 링크 글자에는 매체명만 쓴다 (예: `[연합뉴스](...)`, `[Reuters](...)`). 같은 매체는 매번 같은 이름으로 쓴다.
2. **URL은 검색 결과에 실제로 나온 기사 주소만 쓴다.** 매체 첫 화면이나 섹션 페이지, 추측한 주소는 쓰지 않는다. 기사 주소를 못 찾았으면 그 사실은 쓰지 않는다.
3. **중요한 사실은 두 곳 이상에서 확인한다.** 핵심 3줄과 전망의 근거가 되는 사실은 서로 다른 매체 두 곳 이상의 링크를 단다. 매체끼리 내용이 다르면 둘 다 적고 차이를 밝힌다.
4. **원출처를 우선한다.** 통신사(연합뉴스, Reuters, AP, AFP), 정부·중앙은행·통계기관의 발표, 주요 일간지와 방송을 우선 쓴다. 나무위키, 개인 블로그, 브런치, 커뮤니티 글은 사실의 근거로 쓰지 않는다.
5. **국내·해외 매체를 섞는다.** 한국 소식도 가능하면 해외 매체 한 곳을, 세계 소식도 가능하면 국내 매체 한 곳을 함께 확인해 한쪽 시각에 치우치지 않게 한다.
6. **숫자의 출처를 밝힌다.** 시장 지표 표 아래에 `출처: [매체](URL)` 한 줄을 둔다.
7. **추적 기록에도 출처를 남긴다.** `tracker.json`의 `timeline` 항목과 새 `forecasts`에 `"sources": [{"name": "매체명", "url": "기사 URL"}]`를 넣는다. 시장 가격이 근거인 전망은 그 수치를 보도한 기사를 넣는다.
8. pack 할 때 "출처 링크가 하나도 없는 브리핑" 경고가 나오면 링크를 채운 뒤 다시 pack 한다.

## 전망 작성 원칙 (객관성)

전망은 의견이 아니라 **검증할 수 있는 확률 추정**으로 쓴다.

1. **확률로 쓴다.** "~할 것이다" 대신 시나리오별 확률(5% 단위, 합계 100)을 쓴다. "~할 수도 있다"처럼 틀릴 수 없는 표현은 쓰지 않는다.
2. **근거를 구분한다.** 확률마다 근거가 무엇인지 밝힌다.
   - `시장 가격`: CME FedWatch, 예측시장(Polymarket 등), 선물 가격처럼 돈이 걸린 수치. 있으면 **이것을 우선 쓴다**.
   - `컨센서스`: 기관·이코노미스트 전망치의 중간값.
   - `판단`: 위 두 가지가 없을 때만 쓴다. 이때는 판단 근거가 된 사실을 적는다.
3. **기준선에서 출발한다.** 과거에 비슷한 상황이 얼마나 자주 어떻게 끝났는지(기저율)를 먼저 보고, 이번 사례의 차이만큼 조정한다.
4. **판단을 바꿀 신호를 적는다.** 어떤 지표나 사건이 나오면 전망이 바뀌는지 미리 적는다.
5. **가치 판단을 하지 않는다.** "바람직하다/잘못됐다"가 아니라 "일어날 가능성"만 다룬다. 특정 정당이나 인물에 유리하거나 불리한 쪽으로 확률을 기울이지 않는다.
6. **틀린 것을 기록한다.** 전망 기록은 지우거나 고쳐 쓰지 않는다. 생각이 바뀌면 새 전망을 추가하고, 이전 전망은 마감일에 그대로 채점한다.

## 과거 사례 작성 원칙

- 이슈마다 가장 비슷한 과거 사례를 1~2개 적는다. 억지로 끼워 맞추지 말고, 마땅한 사례가 없으면 "뚜렷한 선례 없음"이라고 쓴다.
- 사례마다 **비슷한 점 / 다른 점 / 당시 결과**를 반드시 함께 적는다. 다른 점을 빼면 안 된다.
- 연도, 수치, 결과는 확인된 사실만 쓴다. 기억이 불확실하면 검색해서 확인한다.
- 과거 사례는 참고일 뿐 같은 결과를 보장하지 않는다는 점을 전제로 쓴다.

## 이슈 추적 규칙 (`W/tracker.json`)

- **issues**: 며칠 이상 이어질 굵직한 이슈만 추적한다 (보통 5~10개).
  - 새 소식이 있으면 `timeline` 맨 앞에 `{"date": "YYYY-MM-DD", "text": "한 문장", "sources": [{"name": "매체명", "url": "기사 URL"}]}`을 추가하고 `summary`, `updated`를 고친다.
  - 새 소식으로 판단이 바뀌면 `outlook`(text, scenarios, signals)을 갱신한다. 확률 합계는 100이어야 한다.
  - 새로 떠오른 큰 이슈는 추가한다. 2주 넘게 새 소식이 없으면 `status`를 `"소강"`으로, 끝났으면 `"종료"`로 바꾼다 (삭제하지 않는다).
  - `area`는 `세계 정치`, `세계 경제`, `한국 정치`, `한국 경제` 중 하나다.
- **forecasts**: 나중에 맞았는지 틀렸는지 판정할 수 있는 문장만 쓴다 (주체, 사건, 기준 수치, 마감일이 분명해야 함).
  - 새 전망은 하루 0~3개 정도만 추가한다. id는 `F-YYYYMMDD-NN`, probability는 5~95 정수로 쓰고, 근거 기사를 `sources`에 넣는다.
  - 전망에는 `kind`를 적는다: 매일 브리핑에서 만든 것은 `"일간"`, 주간 요약에서 만든 것은 `"주간"`, 월간 요약에서 만든 것은 `"월간"`.
  - 채점은 아래 "전망 자동 점검 규칙"을 따른다.
- **indicators**: 매일 한 줄씩 `{"date": "오늘", "values": {"코스피": 숫자, "원/달러": 숫자, "S&P 500": 숫자, "나스닥": 숫자, "브렌트유": 숫자, "미 10년물 금리": 숫자, "미 기준금리(상단)": 숫자}, "note": "기준 시점 설명", "sources": [...]}` 를 추가한다.
  - 지표 이름은 위 7개로 고정한다 (이름이 같아야 주간·월간 흐름이 이어진다).
  - 값은 검색 결과에서 확인한 종가만 쓴다. 확인하지 못했거나 매체마다 다르면 `null` 로 둔다. 휴장일에는 마지막 거래일 값을 쓰고 `note` 에 적는다.
- **issues[].history**: 시나리오 확률의 변화 기록이다. pack 이 자동으로 남기므로 직접 고치지 않는다.

## 전망 자동 점검 규칙

전망을 기록만 하고 끝내지 않도록, 마감일이 지나면 **다음 실행에서 자동으로 채점**한다 (todo 가 알려 준다).

1. 전망 문장(`claim`)을 **쓰인 그대로** 판정한다. 나중에 뜻을 넓히거나 좁혀 해석하지 않는다.
2. 검색으로 결과를 확인하고 다음 중 하나로 정한다.
   - `"발생"`: 문장대로 일어났다.
   - `"미발생"`: 마감일까지 일어나지 않았다.
   - `"판단불가"`: 문장이 모호하거나 확인할 자료가 없다. 이 경우 `note` 에 이유를 쓰고, 다음 전망부터는 더 분명하게 쓴다.
3. `resolved` 에 판정한 날, `note` 에 판정 근거 한 문장, `result_sources` 에 결과를 확인한 기사 링크(`[{"name", "url"}]`)를 넣는다.
4. 확률, 문장, 마감일은 절대 고치지 않는다. 틀린 전망도 그대로 남긴다.
5. 채점 결과는 오늘 브리핑의 "✅ 지난 전망 점검"에 `[발생/미발생] 전망 문장 (당시 N%, 일간/주간/월간) — 판정 근거 ([매체](URL))` 로 쓴다.

## 주간·월간 요약 규칙

todo 가 알려 줄 때 쓴다. 주간은 보통 월요일(지난주 월~일), 월간은 보통 매달 1일(지난달)에 나온다.
요약은 새 뉴스를 찾는 글이 아니라 **그 기간의 브리핑과 tracker 기록을 모아 흐름을 보여 주는 글**이다. 기간 안의 브리핑을 모두 읽고 쓴다. 웹페이지는 기간 동안의 지표 변화, 이슈별 확률 변화, 전망 채점 결과를 표로 자동으로 보여 주므로, 요약 글은 해석에 집중한다.

**주간 요약** (`W/summaries/week-월요일날짜.md`)

```markdown
# 주간 요약 — YYYY년 M월 D일 ~ M월 D일

> 이번 주 핵심 3줄
> 1. ...

## 📈 이번 주 흐름
- 이슈별로 한 주 동안 무엇이 바뀌었는지 2~3문장. 확률이 바뀐 이슈는 "A 시나리오 N% → M%" 와 바뀐 이유를 쓴다.

## 🔁 과거와 비교
- 이번 주 흐름과 비슷했던 과거 시기 1~2개 (비슷한 점 / 다른 점 / 당시 결과)

## ✅ 이번 주 전망 점검
```
